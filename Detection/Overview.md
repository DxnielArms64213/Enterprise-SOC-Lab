# Detection Engineering

## Overview

The Detection phase of the Enterprise SOC Homelab focuses on identifying suspicious activity from security telemetry collected from the lab's endpoints and infrastructure.

The goal is not simply to generate alerts, but to develop, test and validate detections that can identify meaningful security behaviour while reducing unnecessary alerts.

The detection workflow used throughout the lab is:

```text
Security Activity
       │
       ▼
Endpoint Telemetry
       │
       ▼
Wazuh Analysis
       │
       ▼
Detection Rule
       │
       ▼
Alert
       │
       ▼
Triage
       │
       ▼
Investigation
       │
       ▼
Incident Response
```

Detections are developed using telemetry generated by systems within the SOC environment, including Windows Security logs and Sysmon events from `WIN-CLIENT`.

## Detection Development Process

Each detection is developed and tested using a consistent process:

1. Identify a security behaviour that should be detected.
2. Generate the behaviour in the controlled lab environment.
3. Inspect the telemetry received by Wazuh.
4. Identify the relevant event fields and values.
5. Create a Wazuh detection rule.
6. Validate the Wazuh configuration.
7. Test the detection using a controlled positive test.
8. Perform a negative test to confirm that normal activity does not trigger the detection.
9. Document the detection and its results.

This process helps ensure that detections are based on observed telemetry rather than assumptions about how events should appear.

## Detection Sources

The primary detection sources in the lab include:

* Windows Security Event Logs
* Sysmon telemetry
* Wazuh Agent telemetry
* Active Directory security events
* Network and process activity generated during controlled attack simulations

These sources provide different levels of visibility into activity occurring within the Windows environment.

## Custom Wazuh Rules

Custom detections are stored in the Wazuh Manager's local rules configuration.

Custom rules are developed to identify specific behaviours that are relevant to the SOC environment.

The first custom detection developed in the lab is:

| Rule ID  | Detection                  | Data Source       | Status |
| -------- | -------------------------- | ----------------- | ------ |
| `100002` | PowerShell encoded command | Sysmon Event ID 1 | Tested |

## Detection Testing

Detection testing uses both positive and negative test cases.

A **positive test** deliberately generates the behaviour that the detection is designed to identify. The expected result is that the corresponding Wazuh alert is generated.

A **negative test** generates similar but benign activity that should not satisfy the detection conditions.

Using both test types helps determine whether a rule detects the intended behaviour while avoiding unnecessary alerts from normal activity.

## Future Detections

Additional detections will be developed as the SOC environment progresses.

Planned detection areas include:

* Failed Windows logons
* Suspicious process execution
* Account and security group changes
* Persistence mechanisms
* Suspicious network activity
* Additional PowerShell activity
* Multi-event or correlation-based detections

The detections will later be used during controlled attack simulations performed from Kali.

## Detection-to-Incident Workflow

Once the detection phase is sufficiently developed, alerts will be used to exercise the wider SOC workflow:

```text
Controlled Attack
       │
       ▼
Endpoint Activity
       │
       ▼
Sysmon / Windows Logs
       │
       ▼
Wazuh Detection
       │
       ▼
Alert
       │
       ▼
Triage
       │
       ▼
Investigation
       │
       ▼
MITRE ATT&CK Mapping
       │
       ▼
Incident Response
       │
       ▼
Incident Documentation
```

This allows the project to progress from individual detection rules into realistic SOC investigation and incident-response exercises.
